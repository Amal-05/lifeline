# Lifeline mesh protocol (M3)

The transport uses Google Nearby Connections `P2P_CLUSTER` with service ID `org.lifeline.mesh.v1`. On connection, peers exchange a `Hello` containing protocol version, device ID, battery, Internet availability, an inventory Bloom filter, and highest HLC per origin. Peers use the Bloom filter to offer missing signed event envelopes. Relays must preserve signed event bytes. Mutable relay metadata is outside the signed event: `hops` starts at 0 and increments per forward, `ttl` starts at 12 and decrements, and the outer frame carries a coarse `priority_hint` from 0 to 3. Drop at `ttl <= 0`, `hops >= 12`, duplicate event ID, rate limit (10 events/minute/origin), or invalid event signature. Gateways submit stored events to `/api/v1/sync`, where Ed25519 verification is authoritative.

Each transfer frame is at most 32 KiB. Larger event payloads use numbered 23 KiB chunks with a content hash and are reassembled before event validation. A node keeps at most 5,000 events or 20 MiB, whichever limit is reached first; on capacity pressure it evicts delivered events, then lower-priority and older entries, and never evicts its own undelivered SOS. A node maintains at most four connected peers; use the platform cluster strategy and prefer peers with a gateway route. Relay only unseen events and exclude the sender from fan-out. Below 30% battery, discovery runs for 10 seconds every minute; below 10%, relay stops except for the device's own SOS. Android peers verify the Ed25519 signature before relaying; gateways repeat verification before persistence. The inventory filter uses 49,000 bits and seven hashes, targeting a false-positive rate below 1% at the 5,000-event cap. Gateway acceptance is broadcast as a `Delivered` receipt and relayed to neighbours. Media attachments are not relayed by Android.

The Android client uses Nearby Connections `P2P_CLUSTER` discovery/advertising, requests runtime nearby permissions, caps active peers at four, and persists its priority ledger through an atomic local file. It exchanges peer inventory and HLC summaries and retains hop/TTL metadata across storage. Its JVM test suite includes a pure-Kotlin degree-four 100-node convergence harness. The client has gateway upload and delivery receipt support. Android SOS payloads use libsodium `crypto_box_seal` with the coordinator public key returned by `/api/v1/config`; the event signature covers the ciphertext. The API stores the signed ciphertext and decrypts only when triage projects it. Mesh relay rejects plaintext events. Physical two-phone validation still requires compatible Android devices with Google Play Services.
